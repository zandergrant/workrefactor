Build a dashboard that helps decisions

Start with the few operational measures that help someone make a decision, then check where each figure comes from and who can act on it.

I find a dashboard most useful when the measures help someone decide what to do next. It's easy to keep adding charts because the data is available, only to reach the next meeting and discover that nobody can see which issues actually need attention.

This guide uses a request workflow as the example. The goal is a small dashboard that helps the team spot delayed work, assign ownership and see whether the process is getting better.

Download the sample dashboard workbook

Start with decisions, not charts

Ask who will use the dashboard and what they need to do differently after viewing it. For a team managing incoming requests, four questions may be enough:

  1. How much work is open right now?
  2. Which requests are overdue or blocked, and who owns them?
  3. Is new work arriving faster than the team completes it?
  4. Is the time to completion improving without an increase in errors?

You don't need a chart for everything. A small table of overdue items with an owner and next action may be more useful than a decorative pie chart.

Use definitions people can agree on

Metric Working definition Risk if unclear
Open requests Requests not marked Complete or Cancelled Counts differ between teams
Overdue requests Open requests with due date earlier than today Excludes requests with missing dates unless separately flagged
Unassigned work Open requests with a blank owner Work can sit without anyone noticing
Completion rate Completed requests / requests received in the same defined cohort or period Backlog changes can distort a raw ratio
Cycle time Completed timestamp minus created timestamp Calendar time is not the same as active effort
Blocked share Blocked requests / all open requests Teams may avoid using Blocked if it's treated as failure

Document the time window, exclusions and timezone. A KPI that changes definition every month cannot reliably show progress.

The sample workbook

The workbook contains fictional request records and a simple, formula-driven summary. It is meant to show the structure, not represent actual performance. Replace the data with your own only after confirming that status values and date fields are consistent.

The useful part isn't the appearance of the dashboard; it is the connection to the underlying records. Every total should be explainable by filtering the source data. If the dashboard and the sheet disagree, don't polish the chart. Fix the definition or transformation.

Establish a meeting routine

Review exceptions first: overdue, blocked and unassigned. Decide the next action and owner. Then review whether arrival volume or completion capacity has changed enough to require staffing or process changes. End by checking whether last week's actions actually resolved the issues.

A useful dashboard should reduce the effort of preparing for a status meeting. If someone still spends every Monday recreating the same chart, I would examine how the underlying information is collected before redesigning the presentation.
