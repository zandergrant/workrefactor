Turn a spreadsheet into an operations app

Edit a fictional request in either the sheet or app view, then use the Apps Script starter to build an internal prototype.

For a small operational workflow, a spreadsheet can be a useful place to hold the records because people know where the information lives and can inspect or correct it directly. As the workflow grows, the team may benefit from a simpler interface for the people who need to take action without navigating the raw sheet.

One option is to keep the spreadsheet as the shared source of records and build a focused web interface that helps people find, update and review requests. The sheet remains editable, with both views working from the same underlying information.

What makes it work

1. One way for requests to come in

A form or team-owned intake process collects the minimum required information. Every item gets a stable ID, creation date, request category, owner, priority and status. Avoid asking for fields that nobody will use to make a decision.

2. One place for up-to-date records

Google Sheets holds one row per request. A small Apps Script validates incoming values, prevents duplicate IDs, records timestamps and handles updates. In a real implementation, permissions matter: people should only be able to view or edit the data they are authorized to access.

3. A simpler view for the people doing the work

A request owner may need a short list of overdue items and a way to mark one complete. An operations lead may need counts by status, owner and risk. Neither should need to find the right column in a 700-row sheet to do their daily work.

Build a small working version with Google Sheets and Apps Script

The Apps Script starter project contains four complete files: server-side Apps Script, an HTML interface, a stylesheet and the client-side JavaScript. It supports creating, listing, filtering and updating requests. It is a starter, not a production-hardened application.

  1. Create a new Google Sheet using the request tracker workbook as a reference. For the Apps Script starter, use a tab named Requests and the columns specified in the setup instructions.
  2. Open Extensions → Apps Script from that spreadsheet. Create the four files included in the starter, preserving their names.
  3. Run setupRequestSheet() once from the editor, review the authorization prompt and confirm the sheet has the expected headers.
  4. Run the project as an internal web app. Choose an access setting appropriate for your organization. Do not deploy operational data as a public, anonymous app.
  5. Test creating a request, changing a status in the app, and inspecting the sheet to confirm the row was updated. Then edit a field in the sheet and refresh the app to confirm the change appears.

Google's HTML service guide documents web app deployment, and its best-practices guide covers separating interface code and using asynchronous google.script.run calls.

Where this approach works well

Use it for a small, internal workflow with a manageable number of records, a limited set of authorized users, and a clear owner. Intake queues, client setup, internal approvals, facilities requests, content calendars and program scheduling are all reasonable examples.

Don't use it merely because it is cheap to start. A sheet-backed app can become awkward when you need high transaction volumes, complex relationships, strict row-level permissions, detailed audit logging or business-critical uptime. At that point, a proper database or an established system may be the simpler choice overall.

Before you roll it out

Test conflicting edits, accidental deletion, unexpected values and permission boundaries. Back up the sheet. Assign one person to own the workflow and the script. Document where errors appear and what people should do when the app is unavailable. The underlying sheet is an asset because it stays accessible, but only if changes are controlled and recoverable.

For a nontechnical version of this exercise, start with the business request tracker. To decide whether to build at all, use the spreadsheet-versus-app decision guide.
