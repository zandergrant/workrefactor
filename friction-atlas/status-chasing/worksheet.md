# How to Stop Chasing Project Status Updates at Work

**How Work Runs · Operational Friction Atlas**
https://howworkruns.com/friction-atlas/status-chasing/

This worksheet describes a fictional process and a possible redesign. It is not a measured case study or a prediction of time saved. Replace these assumptions with observations from your own team.

## Recognize the symptoms
- [ ] A weekly report is recreated from information already stored in other places.
- [ ] Meetings are dominated by asking whether something is done.
- [ ] Employees receive status questions about records they updated earlier.

## Current state: trace the work
1. **Employee** — Updates personal tracker. Work status is local.
2. **Team lead** — Requests status by message. Information arrives at different times.
3. **Manager** — Rebuilds weekly overview. Spreadsheet becomes stale.
4. **Team** — Discusses unclear cases. Questions repeat.

## Possible future state
1. **Work owner** — Updates shared case. Status and next action defined.
2. **Rule** — Flags missing or stale updates. Owner receives focused prompt.
3. **Team lead** — Reviews exceptions only. Blockers and dates visible.
4. **Manager** — Uses same live view. No parallel report needed.

Why the redesign might help: The redesigned system treats status as part of completing the work, not a separate weekly performance ritual. A shared definition of blocked, owner, next action and last meaningful update provides much of the clarity a reporting layer tries to reconstruct.

## Investigation
List the three questions a manager asks most often. For each, trace where the answer originates, how it reaches the manager, and which step makes it unreliable. If the answer exists but is hard to find, the fix may be navigation. If it does not exist, a dashboard cannot invent it.

## Changes to test
1. **Define a minimum record** — Use one owner, a small set of unambiguous statuses, a next action and a date. Avoid a field unless someone will act on it.
2. **Update at the source** — Make updating the shared status part of the work transition, such as accepting a request or recording a decision.
3. **Design for exceptions** — Highlight blocked, overdue and ownerless records rather than making someone read every healthy case.
4. **Retire a report** — Once the shared view is trusted, deliberately stop preparing one redundant summary. Otherwise the new system adds work instead of replacing it.

## Risks and exceptions to check
Too much visibility can become surveillance. The goal is to make coordination easier, not record every minute an employee spends on a task. Agree on meaningful state changes and give teams room to perform the work without constant updates.

## A smaller alternative
When the actual work is already managed reliably in another platform, build a read-only consolidated view before asking employees to update a second tool. A shared sheet may be useful as a first iteration, but it should not become another unofficial source of truth.
